     3 ОПИС ВИКОНАНОЇ РОБОТИ
     Історія Bolt почалася у 2013 році в Естонії як невеликого стартапу Taxify, що фокусувався виключно на агрегації послуг таксі. Після стрімкого масштабування на країни Європи та Африки компанія трансформувала свою систему у повноцінну суперапп-екосистему. 
     За десять років архітектура еволюціонувала від простого моноліту на PHP до складної децентралізованої платформи мікросервісів, що обслуговує понад 150 мільйонів користувачів та інтегрує таксі, доставку їжі, каршерінг і прокат електросамокатів. 
     Сучасний Bolt – це система, розрахована на обробку колосальних масивів геоданих та фінансових транзакцій у реальному часі. Головним викликом платформи є забезпечення стабільного метчингу сотень тисяч водіїв та клієнтів із мінімальною затримкою. Для вирішення цього завдання було здійснено міграцію з традиційних СУБД на розподілені бази даних та впроваджено подієво-орієнтовану асинхронну модель обробки. 
     Назва інструменту та версія: Gemini 2.5 Flash. 
     Мета використання: з'ясувати причини міграції на розподілену SQL-базу TiDB та її переваги для фінансових транзакцій. 
     Запит (Prompt): "Explain the technical reasons why Bolt migrated to TiDB instead of traditional sharded MySQL, and how it ensures strong consistency for billing." 
     Внесок автора: проаналізовано переваги розділення рівнів обчислень та зберігання, виокремлено значення алгоритму Raft для узгодженості даних. 
     Основним архітектурним стилем Bolt є Подієво-орієнтована мікросервісна архітектура (Event-Driven Microservices) на базі Node.js. Замість моноліту система складається з понад 1000 автономних сервісів. Додатково застосовуються такі патерни: 
     - Stateless Architecture: мікросервіси не зберігають локального стану, що дозволяє миттєво масштабувати їх під час пікових навантажень;
      - Geospatial Indexing (на базі гексагональної сітки H3): оптимізація просторових запитів для пошуку найближчих авто без навантаження на основну БД; 
     - Asynchronous Messaging (через Kafka): гарантована доставка подій між ізольованими доменами системи. 
     Назва інструменту та версія: Gemini 2.5 Flash. 
     Мета використання: отримати опис механізму асинхронної взаємодії мікросервісів під час замовлення поїздки. 
     Запит (Prompt): "Describe the event-driven interaction in Bolt's architecture using Apache Kafka and Node.js when a user creates a ride request." 
     Внесок автора: систематизовано етапи публікації та споживання подій, описано процес ізоляції запису в базу даних від логіки пошуку водія. 
     Архітектура системи розділена на такі ключові компоненти: - Microservices Tier (Node.js/TypeScript): рівень обробки бізнес-логіки. Використання однопотокової моделі Node.js ідеально підходить для високонавантажених I/O-операцій без блокувань ресурсів.
     - Data Storage (TiDB): розподілена SQL-база даних, яка щоденно витримує понад 35 тисяч складних транзакцій на секунду, гарантуючи фінансову точність.
     - Event Bus (Apache Kafka): центральний брокер повідомлень, через який проходять асинхронні процеси, такі як розрахунок динамічного ціноутворення та метчинг. 
     - Geo-Engine: система обробки координат із застосуванням просторових індексів, що дозволяє аналізувати баланс попиту та пропозиції в конкретних районах міста за лічені мілісекунди. 
     Взаємодія підсистем реалізована за подієво-орієнтованим принципом. При створенні замовлення клієнтський додаток звертається до API Gateway. Сервіс замовлень (Order Service) фіксує транзакцію в базі даних TiDB і паралельно публікує подію "order_created" у Kafka, повертаючи клієнту успішну відповідь. Matching Service асинхронно споживає цю подію, розраховує гео-індекс та знаходить найближчого водія. Після згоди водія генерується подія "driver_assigned", яка оновлює стан замовлення. Це гарантує безперебійність: якщо сервіс пошуку тимчасово недоступний, подія чекатиме в черзі Kafka. Перехід до сучасних архітектурних рішень забезпечив такі переваги:
      - Масштабованість бази даних: TiDB дозволяє динамічно додавати вузли зберігання даних, уникаючи складного ручного шардингу та переписування коду. 
     - Висока пропускна здатність: Використання Node.js оптимізувало обробку величезної кількості одночасних мережевих з'єднань. 
     - Відмовостійкість: Розгортання у кількох зонах доступності AWS дозволяє миттєво перенаправляти трафік у разі відмови окремих серверів.
     - Гнучкість інновацій: Незалежні мікросервіси дозволяють легко інтегрувати нові продукти (Bolt Food, оренда самокатів) без ризику для основної платформи.

Рисунок 1 – Діаграма послідовності
       
       Діаграма на рисунку 1 демонструє асинхронний цикл обробки замовлення поїздки. Весь процес розділений на транзакційну фіксацію та подієво-орієнтований пошук. 
       1. Транзакційна фіксація: Пасажир надсилає запит через API Gateway до Order Service. Цей сервіс гарантовано зберігає стан замовлення у розподіленій базі TiDB, отримуючи підтвердження завдяки принципу Strong Consistency. 
       2. Подієва асинхронність: Order Service публікує подію "order_created" у шину Apache Kafka і миттєво повертає клієнту відповідь про прийняття запиту (інтерфейс очікування). 
       3. Обробка та Метчинг: Matching Service автономно зчитує подію з Kafka, розраховує гео-індекс (H3) та знаходить найближче вільне авто. Водієві надсилається пропозиція поїздки. 
       4. Завершення циклу: Після підтвердження водієм, генерується подія "driver_assigned" у Kafka. Order Service зчитує її, оновлює статус у базі даних та через WebSocket сповіщає пасажира про знайдене авто.


4 ВИСНОВКИ
     Архітектура Bolt є зразковим прикладом еволюції до високонавантаженої екосистеми міської мобільності. Ключовим рішенням стала відмова від монолітних СУБД на користь розподіленої SQL-бази TiDB та впровадження жорсткого стандарту бекенд-розробки виключно на Node.js. Аналіз підтвердив, що поєднання асинхронного однопотокового середовища виконання з надійним брокером повідомлень Kafka та гео-індексацією забезпечує екстремальну масштабованість системи. Ця архітектурна гнучкість дозволила Bolt не лише ефективно керувати глобальною логістикою таксі та мікромобільності, а й готувати інфраструктурний фундамент для майбутньої інтеграції автономних транспортних засобів.
